Open findings — details
CS-001 Auth token — HMAC signature never verified (all 3 devices) Critical 3rd round open

For 3 consecutive rounds, the server accepts connections without verifying the HMAC signature. The verify_auth_token() function exists in code but is not being called inside handle_connection() before data is sent. Root cause is almost certainly a missing function call.

[R3 LIVE] Windows — no token sent → received clipboard data
[R3 LIVE] Linux — fake sig sent → received clipboard data
[R3 LIVE] Android — fake sig sent → received clipboard data
Expected on all: {"status": "rejected"}
Root cause: your handle_connection() is likely structured like this (broken):

async def handle_connection(ws):
  async for msg in ws: ← broadcasts BEFORE auth

It must be:
async def handle_connection(ws):
  token = await ws.recv() ← FIRST
  if not verify_auth_token(token): return ← SECOND
  async for msg in ws: ... ← THEN sync
CS-006 Replay attack — expired tokens accepted (all 3 devices) Medium 3rd round open

Tokens with timestamps 180 seconds in the past accepted on all 3 nodes. This is directly tied to CS-001 — since verify_auth_token() is never called, the timestamp check inside it also never runs. Fixing CS-001 will fix this too.

[R3 LIVE] Sent token timestamp = now - 180s
[R3 LIVE] All 3 nodes: returned clipboard data
Timestamp window check (30s) not executing
Automatically fixed when CS-001 is fixed — verify runs timestamp check internally.
CS-003 Wrong fingerprint accepted — peer not validated (all 3) Medium 3rd round open

Token with fingerprint=WRONGFINGERPRINT00 accepted on all 3 nodes. Same root cause as CS-001 — fingerprint check is inside verify_auth_token() which is never called.

[R3 LIVE] Sent fingerprint: WRONGFINGERPRINT00
[R3 LIVE] All 3 nodes: returned clipboard data
Trusted fingerprint list not checked
Automatically fixed when CS-001 is fixed.
CS-008 Nonce reuse — same nonce accepted twice (all 3 devices) Medium New R3

The same nonce value was sent in two separate connections — both accepted. A nonce cache (short-lived blacklist of used nonces) is needed to prevent an attacker from replaying a captured valid token within the 30-second window.

[R3 LIVE] Nonce "same_nonce_reuse_test" sent twice
[R3 LIVE] Both connections: returned clipboard data
No nonce deduplication in place
Add a set() nonce cache with TTL. On auth: check nonce not in cache → add to cache → auto-expire after 60s using asyncio task or timestamp-based eviction.
CS-009 Linux cert has wrong IP SAN — shows Windows IP Medium New R3

Linux node (192.168.1.11) is serving a TLS cert with IP SAN 192.168.1.5 (Windows IP). Cert was likely copied from Windows instead of regenerated. Strict TLS clients connecting to 192.168.1.11 will get a SAN mismatch error.

Linux node cert SAN: IP Address:192.168.1.5 ← wrong
Expected: IP Address:192.168.1.11
Android cert: DNS:localhost only, Not After: 2126 ← still 100yr
Regenerate cert independently on Linux and Android nodes. Each device must generate its own cert using its own LAN IP as the SAN. Do not copy certs across devices.
